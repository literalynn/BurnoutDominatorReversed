# Changes to PS2Recomp

Complete base kept from `ran-j/PS2Recomp`, at the commit given in `UPSTREAM.json`, under its GPLv3 license. Game files and their translation stay in directories ignored by Git.

## SQRT.S reads ft; VF0 in every context (October 15, 2026)

- `fpu_translator.cpp`: the R5900 encodes `SQRT.S fd, ft` with the operand in the ft field and fs = 0 (unlike MIPS IV, PCSX2 `SQRT_S`); the translation read fs, so every square root in the game returned sqrt(f0). In Burnout Dominator all 778 SQRT.S read f0: vector normalizations failed, car orientation matrices were built from unnormalized rotations (rows of length 0.02 to 0.2, the up row their cross product, so the car bodies were squashed flat and only wheels and lights showed) and distances fed to the camera were wrong. A negative operand now also sets I/SI. Test: `SQRT.S reads its operand from ft`.
- `ps2_runtime.h`: `R5900Context` starts with VF0 = (0, 0, 0, 1), its hardwired value, so threads started by `StartThread` and interrupt handlers no longer see VF0.w = 0.

## VU0 microprograms run to their end (October 15, 2026)

- `PS2Runtime::executeVU0Microprogram` (`ps2_runtime.cpp`): a VCALLMS program ran at most 4096 VU cycles and was then dropped half done, its partial registers copied back to the EE. The EE waits for VU0 until the program ends, so the program now runs to its E bit, with a cap of 2^24 cycles that only stops a program that never ends (reported on stderr). Burnout Dominator's VU0 programs all end within 4096 cycles; programs with longer loops were cut short.

## Save states (October 15, 2026)

- `ps2xIOP/include/ps2x/state_archive.h` (new): `ps2x::StateArchive`, a binary archive where one `serialize()` function per component both writes and reads, with section tags that turn a layout mismatch into an error.
- ps2xIOP: `serialize()` for `IopMemory` (RAM, hardware registers, SIO2 and both DualShock 2), `Spu2`, `IopKernel`, `IopRpcBridge`, `IopCdvd` (machine state only; the disc image handle stays with the process), `IopIntrman`, `IopIoman`, `IopTimrman`, `IopImportRegistry`, `IopEmulator` (modules, scheduled interrupts and callbacks, cycle counters), `IopModuleManager` and `IopSubsystem`; `IopEmulator::idle()`/`IopSubsystem::idle()` tell whether IOP code or an interrupt is in progress. `IopCdvd::Impl` declares `IopCdvd` a friend for this.
- ps2xRuntime: `serialize()` for `PS2Memory` (RDRAM, scratchpad, VU memories, DMA/VIF/GIF registers and queues, PATH3 state, EE timers), `Ps2Ipu`, `VU1Interpreter` (registers and pipelines; decoded and compiled program caches are invalidated), `GS` (frontend registers) with `GSRasterBackend::SerializeState` (implemented by paraLLEl-GS the way its dump parser restores a dump: VRAM, register state, GIF paths, then `clobber_register_state`; the CPU rasterizer refuses), `GifArbiter`, `EeScheduler` (threads, wait objects, alarms, IRQ handlers, events and deadlines, the PAL timing flag) and `PS2Runtime` (kernel heap, syscall overrides, exit handlers), plus the HLE globals of `Syscalls/Helpers/State.h` and of the CD, memory card and SIF stubs, all in `src/lib/ps2_save_state.cpp` (new).
- `EeScheduler::run` serves a pending save or load at the top of its loop, where the native stack is unwound, once `EeScheduler::stateQuiet` (no queued or running guest callback, no HLE wait completion), `IopSubsystem::idle`, an idle IPU and no open host file allow it. An open memory card file makes a save fail with a message instead of saving a host stream.
- `PS2Runtime::requestSaveState`/`requestLoadState` and `RunOptions::stateFile`, `loadStateFile` and `saveStateAtVsync`: F5 saves and F7 loads in the window. The runner takes `--state`, `--load-state` and `--save-state-at`, and `tools/project.py run` passes them on. Files start with `BDRSTATE` and a format version; version 1 lacked the PAL flag and loads as PAL.
- Verified on Burnout Dominator: a state saved at VSync 15400 and loaded in a new process reaches VSync 16500 with RDRAM identical to the run that saved it (`BDR_DETERMINISTIC=1`, same pad script). Test: the IOP emulator test saves an IOP with a loaded RPC server module, resets it, restores it and checks the server and module are back.

## VU MAX, MINI and LOI on raw bits (October 15, 2026)

- `vu/ps2_vu1_upper.inl`, `vu/ps2_vu1_upper_engine.h`, `vu/ps2_vu1_program.h`: VU MAX and MINI (broadcast, I and vector forms) compared operands after flushing denormals to zero. The VUs compare the raw bit patterns as sign-magnitude integers and return an operand unchanged (PCSX2 `fp_max`/`fp_min`), which microcode uses to load integer constants: Burnout Dominator's car microcode builds the GIF REGS word 0x412 with `LOI 0x412` and `MAXi.z vf1, vf0, I`. With the denormal flushed REGS was 0, every car vertex was read as PRIM writes and the player's car was never drawn. `ps2_vu_detail::maxBits`/`minBits` (`ps2_vu1_detail.h`) implement the comparison.
- `vu/ps2_vu1_exec.inl`, `ps2_vu1_program.h`, `ps2_vu1_loop_exec.inl`, `ps2_vu1_region_exec.inl`: LOI stores I as raw bits instead of normalizing it; arithmetic still normalizes I when it reads it.
- `vu_translation_helpers.cpp`, `ps2_float.h`: the COP2 macro VMAX/VMINI use the same raw comparison (`ps2_vmax`, `ps2_vmin`) instead of `_mm_max_ps`/`_mm_min_ps`.
- Tests: `MAXi keeps the raw bits of a denormal I`, `VU0 macro VMAX and VMINI keep raw bit patterns`.

## PATH3 unmask windows (October 15, 2026)

- `ps2_vif1_interpreter.cpp`, `ps2_memory.cpp`: an MSKPATH3 unmask used to send every queued PATH3 packet at once. On the console PATH3 runs while unmasked and a new mask takes effect at the end of the GIF packet in progress (EOP). Burnout Dominator re-uploads its textures every frame through a small VRAM cache, one texture per window of `MSKPATH3 0`, 96 NOPs, `MSKPATH3 1` between draw batches; releasing every upload at the first window left each VRAM slot holding the last texture of the frame, so most draws sampled another texture and palette (multicoloured track). The VIF1 interpreter now counts about one PATH3 qword per VIF1 command in a window, lets whole packets out when a command other than NOP runs or the mask returns (at least the packet in progress), releases everything on FLUSHA and when the stream ends unmasked. Test: `PATH3 unmask window lets one GIF packet through before the mask returns`.
- `ps2_gs_tests.cpp` (paraLLEl-GS replay): `BDR_PGS_REPLAY_TEX` dumps a PSMT8/PSMT4 texture of the recording's initial VRAM through its CLUT, `BDR_PGS_REPLAY_TEXEND` the same texture at the end of the replay for both rasterizers.

## EE floating point: no Inf, NaN or denormals (October 15, 2026)

- `ps2xRuntime/include/ps2_float.h` (new): the EE FPU and the VUs have no infinities, NaNs or denormals. An exponent of 255 is an ordinary value, overflow saturates to +-FLT_MAX, denormals are zero, a zero divisor gives +-FLT_MAX (0/0 included) and square roots take the absolute value (PCSX2 `FPU.cpp` and VU clamping). `FPU_ADD_S`, `FPU_SUB_S`, `FPU_MUL_S`, `FPU_DIV_S`, `FPU_SQRT_S` and the COP2 macro `PS2_VADD`/`PS2_VSUB`/`PS2_VMUL` now follow these rules; host IEEE arithmetic produced Inf, then NaN (Inf * 0), which spread through game state. In Burnout Dominator the post-processing strength became NaN during the race, a strip count derived from it was 0, and the `do { n--; } while (n)` loop of 0x1ba7f8 wrote GIF data past the scratchpad into the timer callback table, so the next timer interrupt jumped to 0x80000000.
- `fpu_translator.cpp`: DIV.S sets D/SD (I/SI for 0/0) instead of a non-EE bit and returns +-FLT_MAX; RSQRT.S computes `fs / sqrt(ft)` instead of `1 / sqrt(fs)`.
- `vu_translation_helpers.cpp`: VDIV returned 0 for a zero divisor, VSQRT 0 for a negative input, and VRSQRT ignored its numerator (`Q = 1 / sqrt(ft)` instead of `fs / sqrt(ft)`); they now use `ps2_fdiv`, `ps2_fsqrt`, `ps2_frsqrt`.
- Rounding stays round-to-nearest; the EE rounds toward zero. Test: `EE float semantics: no Inf, NaN or denormals`.
- `EeScheduler.cpp`: `BDR_WATCH_WORD` reports also print the GPRs; `BDR_WATCH_DUMP=file` saves EE RAM at the first report.

## CVT.W.S truncates (October 15, 2026)

- `ps2_runtime_macros.h`: `FPU_CVT_W_S` rounded to nearest (`nearbyintf`); the EE truncates toward zero and saturates out-of-range values to INT32_MIN/INT32_MAX (PCSX2 `FPU.cpp`). Burnout Dominator's boost gauge (0x21d960) steps a length down with `len = step * cvt((len - 0.001) / step)`: rounding 0.99999 up to 1 left `len` unchanged, the loop never ended and the race stayed frozen at the start with the clock stopped. Test: `CVT.W.S truncates toward zero and saturates`.

## MMI semantics (October 15, 2026)

An audit of the MMI translation against the EE Core Instruction Set Manual and PCSX2's interpreter (`pcsx2/MMI.cpp`) found most HI/LO and permutation instructions wrong: the parallel multiplies and divides (PMULTW, PMULTUW, PMADDW, PMSUBW, PMADDUW, PDIVW, PDIVUW, PDIVBW, PMULTH, PMADDH, PMSUBH, PHMADH, PHMSBH) summed every product into one scalar instead of filling the 128-bit HI/LO pair; PMFHI, PMFLO, PMTHI, PMTLO, PMFHL and PMTHL moved 32 or 64 bits instead of 128 (HI1/LO1 are `hi1`/`lo1`); PEXEH, PEXEW, PROT3W, PREVH, PEXCH, PEXCW, PINTH and PINTEH used wrong element orders; PSLLVW, PSRLVW and PSRAVW shifted rs by rt on four lanes instead of words 0 and 2 of rt by rs with 64-bit sign extension; PADDUH and PSUBUH did not saturate; PSLLH, PSRLH and PSRAH used five bits of sa instead of four.

- `ps2xRuntime/include/ps2_mmi.h` (new, included by `ps2_runtime_macros.h`): reference implementations of these instructions on `R5900Context`.
- `ps2xRecomp/src/lib/mmi_translation_helpers.cpp`, `mmi_translator.cpp`: emit calls to them; the wrong macros (`PS2_PINTH`, `PS2_PEXEW`, `PS2_PMFHL_*`, `_mm_custom_sllv_epi32`...) are removed from `ps2_runtime_macros.h`.
- Burnout Dominator only uses PABSW, PSLLH and PSRAH of these, so its behaviour changes through the PABSW fix below; the rest matters for other games. Test: `MMI instructions use the 128-bit HI/LO pair and EE element orders`.
- `EeScheduler.cpp`: `BDR_RDRAM_DUMP=vsync,file` saves EE RAM at that VSync tick.

## PABSW and PABSH read rt (October 15, 2026)

- `ps2xRecomp/src/lib/mmi_translation_helpers.cpp`: `PABSW rd, rt` and `PABSH rd, rt` took their source from rs, which is always `$zero` in these encodings, so they always returned 0. Burnout Dominator's track streamer (0x305060) uses `pabsw` to tell near track sections (offset −4..4, detailed ring of buffers) from far ones (low-detail pool): every far slot got a detailed buffer at `(index ± 5 or 6) mod 10`, i.e. a section of the wrong part of the track. The lit-geometry renderer then drew unlit meshes (80-vertex batches) with the lit VU1 microcode, whose output buffer holds 76 vertices; the overflow wrote vertex data over the GIF tag template at VU1 qword 1006 and every later kick sent garbage to the GS. Test: the unary MMI case of `code_generator_tests.cpp` now covers PABSW and PABSH.
- `ps2_runtime_macros.h`: `PS2_PABSW`/`PS2_PABSH` saturate like the EE (|0x80000000| = 0x7FFFFFFF, |0x8000| = 0x7FFF).
- Debugging: `BDR_VU_BADKICK_DIR` creates its directory, also catches the first PACKED kick whose data runs past qword 1006, prints the VSync and saves EE RAM (`bad.rdram`); `BDR_TRACE_VIF1_DATA=1` adds the first qword of short V4-32 UNPACKs (microcode parameters); `BDR_PGS_RECORD` flushes its file when its window ends.

## VIF1 UNPACK as on the console (October 14, 2026)

- `ps2_vif1_interpreter.cpp`, following PCSX2 `Vif_Unpack.cpp`: V2 unpacks write x y x y (z and w used to keep old VU memory); V3 unpacks are done like V4, so w is the source element after z; STMOD mode 3 also stores the data in ROW; a filling write (WL > CL) writes the next source vector again without consuming it, instead of ROW. Test: `VIF UNPACK V2 repeats xy, V3 reads w from the next element, mode 3 sets ROW`.
- Debugging: `BDR_TRACE_VIF1=first,count` prints the VIF1 commands of some VSync ticks with their TOPS/ITOPS/BASE/OFST/DBF/CYCLE/MODE state; truncated UNPACKs are reported.

## GIF FLG 3, DMA scratchpad bit, GIF and VIF order (October 14, 2026)

- `vu/ps2_vu1_core.cpp`: XGKICK treats a GIF tag with FLG 3 as IMAGE, as the GS manual defines it. It used to report a reserved instruction (code 0xFFFFFFF8, logged as `[VU1 reserved lower] pc=0x18e8`), drop the packet and stop VU1; Burnout Dominator's VU1 microcode kicks such packets from the car select on. `gs/gs_frontend.cpp` (CPU frontend), `gs/ps2_gif_arbiter.cpp` and `ps2_vif1_interpreter.cpp` (pending image data) treat FLG 3 the same way. Test: `XGKICK sends a FLG 3 GIF packet like an IMAGE one`.
- `ps2_memory.cpp`: DMA addresses with bit 31 (SPR) set read the scratchpad, in normal mode, for chain tags and for chain data; the chain walker no longer masks that bit out of DMAtag addresses. The EE's own accesses keep reading 0x8xxxxxxx as KSEG0 RAM.
- `ps2_memory.cpp`: `processPendingTransfers` sends the GIF DMA packets to the GS before running the VIF transfers of the same batch; the arbiter's path priority used to put the PATH1/PATH2 packets those produce ahead of them. With a GS that keeps path state, the native GIF upload shortcuts are skipped.
- Debugging: `vu/ps2_vu1_core.cpp` `BDR_VU_BADKICK_DIR` (BOOT.md §10); `BDR_TRACE_DMA_CHAIN=N` prints the tags of up to N DMA chains over 512 KiB; `BDR_PGS_RECORD_FROM`/`BDR_PGS_RECORD_VSYNCS` limit a paraLLEl-GS recording to some VSync ticks; `BDR_PROFILE_STACKS=N` prints N call stacks of the profiled thread. `scripts/Invoke-MSBuild.ps1` also finds the MSBuild of a Visual Studio instance left incomplete by an interrupted update.

## paraLLEl-GS backend (October 14, 2026)

The GS can now run on [paraLLEl-GS](https://github.com/Arntzen-Software/parallel-gs) (Arntzen Software, LGPLv3), which emulates the GS with Vulkan compute, following upstream PS2Recomp pull request #285 (work in progress). The CPU rasterizer stays as the fallback when no Vulkan device is found, and for the tests.

- `ps2xRuntime/cmake/ParallelGS.cmake`, `ParallelGSPatches.cmake` (new): `PS2X_GS_BACKEND=PARALLEL_GS` fetches paraLLEl-GS at commit 3a66c19 (`FETCHCONTENT_SOURCE_DIR_PARALLEL_GS` accepts a local checkout), builds it with the DLL runtime and debug info, and patches two sources at configure time: the transfer tail fix of #285, and `compute_page_rect`, whose block count wraps to about 2^32 for a texture larger than a page row at a base that is not page aligned (an endless loop in Burnout's intro); such a rect is now treated as straddling. `ps2xRuntime/CMakeLists.txt`: the option.
- `ps2xRuntime/src/lib/gs/gs_parallel_backend.cpp`, `include/runtime/gs/gs_parallel_backend.h` (new): the backend, adapted from #285. It creates its own Vulkan device and reads the scanout image back to host memory, instead of #285's Vulkan-to-OpenGL interop, so the window, frame dumps and headless runs all use the usual `PresentationFrame` pixels. It follows transfers for `GetTransferSnapshot`, maps SIGNAL, FINISH and LABEL to CSR and SIGLBLID, and records its input with `BDR_PGS_RECORD`.
- `gs_backend.h`: `UsesRawCommands`, `ProcessGIF`, `WriteRegisterRaw`. `gs_frontend.h/.cpp`: `processGIFPacket` takes the GIF path; with a raw backend, GIF packets, register writes and native image uploads go to the backend unparsed, and the frontend's framebuffer clears are refused. `ps2_gif_arbiter.h/.cpp`: the packet callback receives the path. `vu/ps2_vu1_core.cpp`: XGKICK without an arbiter uses PATH1.
- `ps2_memory.h`, `ps2_vif1_interpreter.cpp`: `setGifPathsKeepTagState`. paraLLEl-GS, like the GS, keeps each path's GIF tag state between packets. A VIF1 DIRECT whose image data comes in the next DIRECT was re-sent under a synthetic IMAGE tag (for the CPU frontend, which parses every packet from a tag); the GS then read that second tag as pixels and lost track of PATH2 (giant triangles, black screen). With a raw backend, DIRECT payloads now go out as they are.
- `ps2_runtime.cpp`: `syncCoreSubsystems` selects paraLLEl-GS unless `PS2X_GS_BACKEND=cpu`, in windowed and headless runs. `Kernel/Syscalls/System.cpp`: `GsSetCrt` also sets SMODE1 (CMOD, LC) as the BIOS does (from #285); paraLLEl-GS derives the video mode from it.
- Tests: `paraLLEl-GS draws a PACKED A+D sprite into VRAM` (sprite, scanout, PATH2 IMAGE upload); `paraLLEl-GS replay matches the CPU rasterizer` replays a `BDR_PGS_RECORD` file into both backends (`BDR_PGS_REPLAY`, BOOT.md §10). `ps2xTest/src/main.cpp` sets `PS2X_GS_BACKEND=cpu`, since runtime tests read the guest-side VRAM.

Result (Windows, RTX 5090): the intro and the 50 Hz / 60 Hz screen run at 50–54 VSync/s instead of 34.

## Texture page cache (October 14, 2026)

- `ps2xRuntime/include/runtime/gs/gs_texture_page_cache.h`: each cache keeps 64 page copies instead of one. The page being read still keeps the bytes it had when it was loaded until another page is read or TEXFLUSH, as before; a page read again reuses its earlier copy only when no VRAM write touched it since, so it returns the same bytes as a fresh copy. Before, every page change copied 8 KiB: with bilinear filtering on textures spanning several pages, that was one copy per texel, about a quarter of a raster worker's time in a race (`BDR_PROFILE_THREAD=GSRaster0`).
- `ps2xRuntime/include/runtime/gs/ps2_gs_memory.h`: `PixelStorageTraits::Write` (no longer `constexpr`) marks the written page in `g_pageCopyHolders`, which every cache checks before reusing a copy.
- `ps2xRuntime/src/lib/gs/gs_cpu_backend.cpp`: raster workers are named `GSRaster<N>`; bilinear channel interpolation rounds by adding 0.5 instead of calling `std::lround` (the value is never negative).
- `gs_cpu_backend.cpp`: `BDR_GS_STATS=1` prints queue counters once a second (BOOT.md §10).
- Test: `gs_cache.memory.reload_after_write`.

## Memory card saves (October 14, 2026)

- `Kernel/Stubs/MemoryCard.cpp`: a libmc command is refused with -200 while the previous one has not been reported by `sceMcSync`, as libmc 3020 does when `PollSema` on its semaphore fails (0x3B5588: `sceMcWrite` returns 0xFFFFFF38). The runtime completes commands at once, so "running" now lasts until the result is collected. Burnout's save (state 0x47 of 0x3985F8) calls `sceMcWrite` then `sceMcFlush` without syncing (0x396B90 in between is empty): on the console the flush is refused and the next `sceMcSync` reports the write; here the flush used to replace the pending write result, the game saw 0 bytes written against the expected size and showed "Save failed". With the fix, creating a profile writes `view.ico` (65,872 bytes), the data file `BESLES-54627-BD` (43,996) and `icon.sys` (964), and the game shows "Save Successful". `sceMcOpen` now logs its path, mode and result like the other calls. Test: `sceMc refuses a command until sceMcSync reports the previous one` (456/456).
- `gs_frontend.cpp`: `BDR_TRACE_GS_VSYNC=N` traces every primitive submitted during VSync tick N.
- `ps2_runtime.cpp`: dumped frames are named `frame_NNNNN_vTTTTTT.png` with the VSync tick, to place `BDR_PAD_SCRIPT` presses.

## Checkpoint unwinding and interrupt masking (October 14, 2026)

- `ps2xRuntime/include/runtime/ee_unwind.h` (new), `ps2_runtime.cpp`, `EeScheduler.cpp`: when a checkpoint asks generated code to return to the scheduler, a thread-local flag is set and `dispatchGuestBranch` returns false after any call, instead of comparing `ctx->pc` with the callee's entry. That comparison (meant for handlers that leave `pc` unchanged) mistook an unwinding mutual recursion for a finished call: in Burnout, 0x336458 calls 0x335D88, which calls 0x336458, which calls 0x335D88 again; a checkpoint on that innermost call left `pc` = 0x335D88, the outer call to 0x335D88 was taken as finished, and 0x336458 went on with the inner frames still on the stack and read its return address from the wrong slot. This is the crash of BOOT.md §15 (jumps to 0xB415CB, 0x1, 0x17A, 0x11B...): 3 runs out of 4 under load before, 0 out of 12 after. The scheduler clears the flag before each dispatch; an unneeded unwind only costs a resume through the return address's entry. Test: `dispatchGuestBranch call keeps unwinding when a checkpoint stops at the callee entry` (455/455).
- `EeScheduler.cpp`: queued handlers (INTC, DMAC, alarms, VSync and SIF callbacks) start only when the running thread has EIE set, i.e. not between the game's `di` and `ei`, as on the EE.
- `EeScheduler.cpp`: `BDR_DISPATCH_HISTORY=1` keeps the last 256 scheduler dispatches (thread, pc, sp, ra) and prints them when the scheduler reaches a pc without generated code.

## GS queue and debugging aids (October 14, 2026)

- `gs_cpu_backend.h/.cpp`: CLUT loads, host-to-local and local-to-local transfers, image uploads, TEXFLUSH, framebuffer clears and single-pixel VRAM writes no longer make the submitting thread wait for the raster workers. They are queued with the primitives as serial operations: when the workers reach one, the last to arrive runs it (`std::barrier` completion) while the others wait, so it sees every earlier operation finished and none of the later ones started. A primitive sampling a range written by a queued primitive now queues such a barrier instead of draining. FINISH no longer waits (the game only learns the GS is done; every host read of VRAM still waits). Local-to-host transfers, VRAM reads, snapshots, presentation and reset still drain. The backend destructor drains the queue, so the caller's VRAM holds everything submitted. `GetTransferSnapshot` reports the last requested transfer while workers run. With 8 workers on the intro video: from 25 to 31 VSync/s, game thread waiting on the GS from 42% to about 15–25% of the time.
- `ps2xTest/src/ps2_gs_tests.cpp`: a scene that uploads a 32-bit texture, samples it, overwrites it, samples it again, then loads an 8-bit texture and its CLUT twice (TEX0 with CLD = 1) between draws must give byte-identical VRAM with 4 workers and with immediate drawing. 454/454 runtime tests pass.
- `ps2_ipu.cpp`: the output FIFO is a byte vector with a read index instead of a `std::deque<uint8_t>` filled and emptied one byte at a time.
- `EeScheduler.cpp`: `BDR_DETERMINISTIC=1` lets VBlank, alarms and timers fire on EE cycles alone instead of also waiting for the host clock; idle time is skipped and runs repeat exactly (the guest cycle count at a given VSync is identical from run to run). Game speed is then unrelated to real time. `BDR_WATCH_WORD=0xADDR[:0xVALUE]` checks a guest word after every dispatched function and prints the last 32 dispatched functions when it changes (or becomes VALUE).

## Performance (October 13, 2026)

- `ps2xRuntime/include/runtime/ps2_wait_stats.h` (new), `EeScheduler.cpp`, `gs_cpu_backend.cpp`, `ps2_runtime.cpp`: each `[status]` line reports the share of wall time the game thread spent waiting since the previous one, by cause (`idle`: no EE thread ready; `pace`: an event due in EE cycles waits for host time; `gs`: waiting for the GS raster workers; `gslock`: GS backend held by the presentation thread), and the VSync rate. Owner's profile in the menus: 41% of the game thread's samples in a Windows wait, cause unknown until now.
- `EeScheduler.cpp`: `BDR_EE_CYCLE_SCALE=P` charges P% of the cycles reported at checkpoints (default 100, unchanged behaviour).
- Measured on the CPU rasterizer (one thread, 640x448 sprite): 20 ns per pixel untextured, 43 textured, 62 textured and blended, 134 bilinear.

- `ps2xRuntime/src/lib/gs/gs_cpu_backend.cpp` and `gs_cpu_backend.h`: deferred, multi-threaded CPU rasterization. `Submit` queues primitives; worker threads (`BDR_GS_THREADS`, default half the cores, at most 8; 0 or 1 keeps the former immediate drawing) draw them in interleaved 8-row bands, so each pixel is written by one thread in submission order. Every operation that reads or writes VRAM or the CLUT (VRAM access, transfers, CLUT load, clear, TEXFLUSH, FINISH, presentation, snapshots, reset) waits for the queue first. A primitive that samples a VRAM range written by a queued primitive also waits (render to texture without TEXFLUSH). Each worker has its own texture page cache, invalidated where the former single cache was.
- Same file: triangles are scanned only over the part of each row where the three edge functions can pass (widened by 1e-3 in weight and two pixels); the per-pixel edge test is unchanged.
- `ps2xTest/src/ps2_gs_tests.cpp`: a scene of blended Gouraud triangles with depth test and a render-to-texture sprite sampled without TEXFLUSH must give byte-identical VRAM with 4 workers and with immediate drawing. `main.cpp` keeps the other GS tests, which read raw VRAM right after a draw, on immediate drawing. A 20,000-triangle scene gives the same VRAM hash with and without the row spans. ThreadSanitizer: 453/453 tests, no report.
- `ee_scheduler.h`, `EeScheduler.cpp`: the running thread is cached instead of looked up in the thread map after every guest dispatch (about 8% of the EE thread in a cloud profile); the cache is cleared on every erase. The dispatch loop tests the generated function table inline, and `dispatchGuestBranch` looks a target up once instead of three times.

Digital, analog (0x73) and pressure (0x79) modes, configuration mode (0x43) with status and constants (0x45, 0x46, 0x47, 0x4C), mode switch and lock (0x44), motor mapping (0x4D), response mask (0x4F), poll (0x42) with buttons, sticks, the 12 pressure bytes and the two motor bytes.

## IPU and video (October 7, 2026)

- `ps2xRuntime/include/runtime/ps2_ipu.h`, `src/lib/ps2_ipu.cpp`: IPU hardware model started by Claude, integrated into the runtime. MPEG bit reading, VLC tables, BDEC (dequantisation and IDCT to RAW16), SETIQ/SETVQ/SETTH, CSC and PACK. A command waits for missing data and then resumes, without faking success. IDEC is still not implemented and reports an error diagnostic.
- `ps2_memory.h/.cpp`: 32/64-bit access to the IPU registers, 128-bit access to the FIFOs, DMA channels 3/4 with progressive filling, tag chains and RDRAM/scratchpad destinations. CHCR reads of these channels keep STR set until the transfer ends. The former passive IPU registers are removed.
- `ps2_memory.cpp`: SPR_TO source chains on channel 9 (REF/REFE, CNT, NEXT, CALL/RET, END), gathering the reference blocks libmpeg uses, scratchpad wrap-around and one interrupt per finished chain.
- `ps2xRuntime/CMakeLists.txt`, `ps2xTest/CMakeLists.txt` and `src/main.cpp`: build of the model and test registration. `ps2_ipu_tests.cpp` checks bits and BUSY, an invalid VLC, FIFO pressure on the DMA, a CSC resumed after two transfers, an intra RAW16 macroblock and an SPR_TO chain with wrap-around. The two existing IPU initialisation tests now expect the hardware clearing of RST.
- Windows validation: 449/449 runtime tests, the five IOP suites, SPU2, the Burnout bindings and 43 Python tests pass. These tests do not yet prove that the game's whole intro plays.
- `ps2_ipu.cpp`: BDEC keeps its state after the RAW16 output to wait for the next MPEG code, detects SCD/ECD after stuffing and saturates intra pixels. Optional `BDR_TRACE_IPU` trace. Two more tests cover IPU REF/REFE chains and a late output DMA followed by the start code.
- `ps2xRecomp/src/lib/control_flow_emitter.cpp`: BLEZ/BGTZ/BLTZ/BGEZ, including the likely/link forms, compare the signed 64-bit scalar register. The former 32-bit comparison mistook bit 31 of IPU data for BUSY (bit 63). Test of the twelve variants in `code_generator_tests.cpp`; 452/452 tests pass on Windows. Guest code must be regenerated.

## SIO2 and RPC waits (October 7, 2026)

- `ps2xIOP/src/emulator/core/iop_memory.h/.cpp` and `iop_emulator.cpp`: SIO2 PIO transport for ports without a device. SEND3 delimits packets; DATA_OUT answers `0xFF`, RECV1 reports disconnected ports, INTR is acknowledged by writing 1. CTRL START schedules IOP IRQ 17. Memory cards and controllers are not reported as present. Tests in `iop_import_tests.cpp`.
- `iop_kernel.h/.cpp`, `services/iop_rpc.h/.cpp`, `iop_emulator.cpp`: physical RPC server functions now run in a scheduled temporary thread with a reusable stack. `WaitSema`, `WaitEventFlag`, `SleepThread` and `DelayThread` can therefore suspend the server while other IOP threads and callbacks run. Module entry points and ISRs keep their existing execution path. A server that does not return within its budget produces an explicit error; no incomplete result is sent as a successful reply.
- `iop_emulator.cpp`: `thbase:35–38` (SetAlarm/iSetAlarm/CancelAlarm/iCancelAlarm) schedule and cancel callbacks on the IOP clock, keeping argument and GP. A non-zero callback return re-arms the alarm. A null callback or a clock outside RAM is refused.
- `iop_emulator_tests.cpp`: a synthetic IRX calls GetThreadId, DelayThread, SetAlarm and SleepThread; its iWakeupThread callback wakes it. Checks the thread identity after the wait, the elapsed time and 128 successive calls without running out of stacks. These tests use no game bytes.
- Limits: SIO2 DMA/dmacman transport and attached devices are still missing; priority 100 for temporary RPC invocations. The exact error codes of every alarm operation still have to be compared with Sony's kernel.

- `src/burnout_overrides.cpp`: 28 SDK functions bound to the runtime by address ([SDK_FUNCTIONS.md](SDK_FUNCTIONS.md)) and a ROM0 profile with a 16-byte European ROMVER; checked by `tests/native/burnout_overrides_tests.cpp`.
- Runtime guest memory (`Kernel/Syscalls/Helpers/State.h`, `Helpers/Runtime.h`, `ps2_runtime.cpp`): the RPC, TLS and boot mode pools are relative to a base. It stays 0x01F00000, unless the ELF image goes beyond that address (Burnout: .bss up to 0x01F9BB00, main stack 0x01FF0000–0x02000000). In that case `loadELF` places the pools, the runtime heap (`guestMalloc`) and the callback stacks in 0x00080000–0x00100000, below the image. Before, the runtime heap was empty and pools and stacks overwrote the game's .bss and stack (see upstream #258). Low layout: pools 0x80000–0xB1000, heap 0xB4000–0xC0000, 16 callback stacks of 0x4000 in 0xC0000–0x100000.
- `EeScheduler`: the callback stacks of a deleted thread (`DeleteThread`, `ExitDeleteThread`) go to a free list reused by later threads. Before, every new thread that received a callback took one more stack, never returned, until "EE invocation stack space exhausted".
- `SetupHeap`/`EndOfHeap` (`Syscalls/System.cpp`): in that case the heap belongs to the game's malloc. `SetupHeap` returns its base; with a size of −1, `EndOfHeap` returns the current thread's stack, like the EE kernel. Before, `EndOfHeap` was 0x01F00000, below the 0x01F9BB00 base: every `sbrk` failed, and so did `RwEngineInit`.
- EE → IOP SIF commands:
  - `ps2_stubs::sceSifSendCmd` reads arguments 5 and 6 from `$t0`/`$t1` (EE ABI), fills the packet header like the SDK, copies the extra data into IOP memory and hands the packet to the IOP handler of its command number. It returns a DMA id. `ps2_syscalls::sceSifSendCmd` delegates to it: it used to read these arguments from the stack and copy to EE RAM.
  - `PS2IopTransport::deliverSifCommand` and `IopSubsystem::deliverSifCommand` route this packet.
  - ps2xIOP: sifcmd:8–11 (`sceSifSetCmdBuffer`, `sceSifSetSysCmdBuffer`, `sceSifAddCmdHandler`, `sceSifRemoveCmdHandler`) keep the handler tables (tables in IOP memory, like sifcmd: 8-byte `{handler, harg}` entries for user commands, 12 bytes for the system table). A received packet runs `handler(packet, harg)`.
- ps2xIOP, sifman:32 `sceSifSetDmaIntr`: same transfer as `sceSifSetDma`, then `func(data)` as a callback scheduled after the transfer. Before, the ordinal returned 0 without transferring anything, and GTFSCDVD's read thread slept forever.
- Tests:

Tests: `ps2_spu2_tests` (target in `ps2xIOP/CMakeLists.txt` and `tools/project.py`).

The upstream runtime's hardware calls remain experimental. No game function is replaced by `ret0`, `ret1`, a fake success or a `skip` to get a boot test through.

The engine automatically picks 8 recognised SIF adapters despite the `stubs=[]` list in the configuration. The report and the generated header allow checking them separately; counts of C++ bodies must not be confused with the number of real game functions.
